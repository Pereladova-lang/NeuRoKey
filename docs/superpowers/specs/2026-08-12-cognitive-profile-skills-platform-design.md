# NeuRoKey — Cognitive Profile Engine и система авторских скиллов (Design)

**Дата:** 12 августа 2026
**Статус:** Approved
**Трек:** Проектирование ядра платформы — часть более широкой инициативы (см. раздел "Связанные треки" ниже), выделенной из семи пунктов, поднятых при обсуждении пере-выхода за рамки пилота.

## Контекст

Пилот (`docs/superpowers/specs/2026-07-15-neurokey-pilot-design.md`, реализован в `neurokey-pilot/`) закрывает только когорту 11–14 лет: rule-based движок в `src/lib/engine.ts` выбирает уровень/тип упражнения из 90 заранее написанных вариантов (`src/content/*.ts`). У движка нет входного сигнала об экранной нагрузке — MVP сознательно исключил "полную ИИ адаптивность" и интеграцию с Family Link/Screen Time (`brief.md`, раздел MVP Scope).

Этот спек проектирует следующий слой поверх пилота: возрасто-агностичное ядро платформы, которое (а) строит цифровой когнитивный профиль пользователя, (б) формализует авторскую методику компенсации экранной нагрузки как переиспользуемую структуру данных ("скилл"), готовую и для будущей процедурной генерации упражнений, и для патентной заявки. Пилот как продукт не переписывается — общий код выделяется в отдельный пакет, контент и UI остаются как есть.

### Связанные треки (не входят в этот спек)
- **Патентная/IP-стратегия** — что и как патентовать, договоры соавторства с фиксацией долей, проверка формулировок на медицинские claims. Отдельная юридическая работа, требования к которой отмечены здесь пунктами "передать в трек A".
- **Анализ конкурентов (Kids360)** — маркетинговое позиционирование, не архитектура.
- **Партнёрский product description + правки brief.md** — документация, пишется после того, как это ядро утверждено.
- **Взрослая/родительская версия профиля** — отдельное будущее приложение на этой же платформе; в это ядро закладывается только возрасто-агностичность схемы, не конкретная реализация.

### Явно вне рамок
- Процедурная генерация упражнений из скилла — структура данных проектируется готовой к этому, сам генератор не строится.
- Камера/eye-tracking как источник сигнала — закладывается как расширяемая точка, не реализуется.
- Интеграция с Google Family Link / iOS Screen Time — по-прежнему не в этом спеке.
- Медицинские диагностические формулировки — исключены сознательно (см. раздел 5).

## 1. Границы: пакет `packages/neurokey-core`

Монорепо получает новый workspace-пакет, в который переезжает переиспользуемая часть `neurokey-pilot/src/lib`:

```
packages/
  neurokey-core/
    src/
      engine.ts            # существующий rule-engine пилота (nextLevel, pickSessionTypes,
                            # computeScores, nextStreak, earnedBadges, aggregateWeek) — переезжает как есть
      exercise-types.ts     # существующие типы (CognitiveScores и т.д.)
      cognitive-profile.ts  # новое: CognitiveProfile, AssessmentEngine
      skill.ts               # новое: формат Skill
    package.json
neurokey-pilot/
  # импортирует @neurokey/core вместо относительных путей к src/lib
  src/content/               # контент остаётся здесь — специфика конкретного приложения
  src/components/             # UI остаётся здесь
```

Правило разделения: **пакет — это методика и правила, приложение — это контент и интерфейс**. `neurokey-pilot` — первое приложение на платформе; будущие приложения (другие возрастные когорты как отдельные продукты, взрослая версия, B2B для школ) подключают тот же пакет.

На этом этапе — без отдельного билда/паблиша пакета в реестр, просто чёткая граница workspace внутри монорепо (npm/pnpm workspaces).

## 2. Cognitive Profile

### 2.1 Схема

```ts
type ScaleId = string; // реестр расширяемый; пилот использует только
                        // "attention" | "memory" | "logic" | "control"

interface CognitiveProfile {
  userId: string;
  scales: Record<ScaleId, number>;   // 0–100, как в текущем aggregateWeek
  history: ScaleSnapshot[];           // week-over-week, для дельт и трендов
  baselineCompletedAt: Date | null;
  lastAssessedAt: Date;
}

interface ScaleSnapshot {
  weekStart: Date;
  scales: Record<ScaleId, number>;
}
```

Реестр `ScaleId` — открытый список, не enum. Пилот сегодня заполняет только 4 существующие шкалы; добавление новой шкалы (моторика, психоэмоциональное состояние — упомянуты как будущее направление) не требует изменения схемы `CognitiveProfile`, только регистрации нового `ScaleId` и весов для него в конкретных упражнениях/скиллах.

### 2.2 Источники сигнала (расширяемые, приоритет — от обязательного к опциональному)

| Источник | Статус в пилоте | Что даёт |
|---|---|---|
| Взаимодействие с экраном внутри приложения (тайминг, точность, паттерн ответов) | **Единственный активный источник** | Основа и первичной диагностики, и текущего `aggregateWeek` |
| Агрегированное экранное время устройства (через Screen Time/Family Link) | Не реализован, точка расширения в `AssessmentEngine` | Усиливающий сигнал о типе/длительности нагрузки — опционален, зависит от разрешений ОС и родителя |
| Камера/визуальный канал (eye-tracking, мимика) | Не реализован, точка расширения | Будущий источник; требует отдельной проработки согласий и хранения (биометрия) — вне этого спека |

`AssessmentEngine` принимает сигналы через единый интерфейс `SignalSource`, так что добавление нового источника не меняет вызывающий код:

```ts
interface SignalSource {
  kind: 'in-app-interaction' | 'device-screen-time' | 'visual-channel';
  collect(context: SessionContext): SignalReading[];
}
```

### 2.3 Жизненный цикл профиля

1. **Первичная диагностика (baseline)** — короткая серия игровых заданий при первом запуске, покрывающая все активные шкалы. Формализует и заменяет пункт "встроенные тесты когнитивных функций" из `brief.md` (там был запланирован, но не реализован в MVP).
2. **Динамическое обновление** — после каждой обычной сессии профиль пересчитывается из результатов упражнений (расширение существующего `aggregateWeek`).
3. **Периодическая переоценка** — короткий повторный baseline-тест на регулярной основе (кандидат: раз в месяц, как было в исходном плане `brief.md`), для отделения "шума" отдельных сессий от устойчивой динамики.

### 2.4 Терминология — обязательное ограничение

Продуктовые тексты и код используют формулировки **"оценка когнитивного профиля по игровым и поведенческим реакциям"**. Не используются формулировки, подразумевающие медицинскую диагностику ("анализ дисбаланса функций организма", аналогии с ЭЭГ, постановка состояний). Это не косметика: в РФ формулировки диагностического характера могут потребовать регистрации как медицинское изделие. Финальная проверка формулировок — юристом (трек A), но начиная с этого спека весь новый код и все новые тексты уже следуют этому ограничению.

## 3. Skill — формат авторской методики

### 3.1 Схема

```ts
interface Skill {
  id: string;
  version: string;
  name: string;

  trigger: {
    signalType: 'duration' | 'contentType' | 'combined';
    // конкретные пороги/паттерны — данные, не код;
    // при появлении device-screen-time сигнала contentType может уточняться,
    // но 'duration' остаётся рабочим базовым вариантом даже без него
  };

  targetScales: ScaleId[];             // какие функции компенсирует/развивает

  exerciseParams: {                     // параметры для подбора СЕЙЧАС и генерации ПОЗЖЕ
    typeWeights: Partial<Record<ExerciseType, number>>;
    difficultyAdjustment: number;       // сдвиг относительно текущего уровня
    // дальнейшие поля добавляются по мере перехода к процедурной генерации,
    // не ломая уже сохранённые скиллы (см. 3.3 про версионирование)
  };

  authorship: Contributor[];
  citations: Reference[];

  createdAt: Date;
  effectiveFrom: Date;
}

interface Contributor {
  name: string;
  qualification: string;               // напр. "нейропсихолог, автор методики"
  role: 'methodologist' | 'consultant' | 'technical-partner' | 'investor-partner';
  sharePercent: number;                 // учётное поле — см. 3.2
}

interface Reference {
  citation: string;
  url?: string;
}
```

### 3.2 Авторство и доли — важное ограничение

`Contributor.sharePercent` — это **учётная запись**, не юридический инструмент. Она позволяет вести расчёт (кто сколько должен получить с конкретного скилла или с продукта, использующего этот скилл), включая произвольное распределение (не поровну), с сохранением истории (кто добавлен когда). Она **не создаёт и не подтверждает права** сама по себе — фактические права возникают из договора (соглашение о соавторстве, IP-ассигнация, консультационный договор с роялти). Оформление таких договоров — пункт трека A, обязательный до того, как поле `sharePercent` используется для реальных выплат.

### 3.3 Версионирование

Каждое изменение содержательной части скилла (порог триггера, целевые шкалы, параметры) создаёт новую `version`, старые версии не удаляются — это одновременно (а) история для будущей патентной заявки/приоритета, (б) возможность откатить методику, если новая версия хуже работает на реальных пользователях.

### 3.4 Что скилл даёт пилоту уже сейчас

В пилоте `exerciseParams.typeWeights` соответствует существующему `TYPE_WEIGHTS` в `engine.ts` — то есть можно сформулировать минимальный набор скиллов (по одному на существующий паттерн компенсации), подписать их твоим авторством и научными источниками, и это уже валидный IP-актив — готовый к патентной заявке, без единой строки процедурной генерации.

## 4. Влияние на существующий пилот

- `neurokey-pilot/src/lib/engine.ts`, `exercise-types.ts` физически переезжают в `packages/neurokey-core`, импорты в остальном коде пилота меняются на `@neurokey/core` — поведение не меняется, тесты (`tests/unit/engine.test.ts`) переезжают вместе с кодом.
- Новые модули (`cognitive-profile.ts`, `skill.ts`) добавляются в пакет как чистые функции — без БД-зависимости, тестируются так же, как сегодня тестируется `engine.ts` (юнит-тесты без базы).
- Схема `Child`/`Session`/`SessionResult` в `prisma/schema.prisma` пока не меняется: baseline-тест и периодическая переоценка используют существующую механику сессий (сессия особого типа), новые таблицы для `CognitiveProfile.history` и `Skill` проектируются в отдельном implementation-plan, не в этом спеке.

## 5. Тестирование

Следуя конвенции репозитория (TDD, юнит-тесты без БД для `src/lib`), `cognitive-profile.ts` и `skill.ts` в новом пакете тестируются как чистые функции:
- `AssessmentEngine`: baseline из фиксированного набора `SignalReading[]` → детерминированный `CognitiveProfile.scales`.
- Skill trigger matching: набор `SignalReading[]` + порог скилла → детерминированный выбор скилла.
- Обновление профиля: серия `ScaleSnapshot` → корректный расчёт тренда (аналогично существующим тестам `aggregateWeek`).
